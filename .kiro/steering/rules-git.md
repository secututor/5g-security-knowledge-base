# Git 작업 규칙 (Git Rules)

이 저장소에서 커밋·푸시 등 git 이력을 바꾸는 작업에 대한 **강제 규칙**입니다.
AI 에이전트와 사람 기여자 모두 이 규칙을 따릅니다.
이 파일은 `.kiro/steering/`에 있어 기본 에이전트 세션에 자동 로드됩니다.

---

## 1. 커밋·푸시는 명시적 승인 후에만 (필수)

- **`git commit` 과 `git push` 는 사용자의 명시적 승인 없이 실행하지 않는다.**
- 파일 생성/편집, 검증, `git add`(스테이징)까지는 진행할 수 있으나,
  **커밋과 푸시는 반드시 사용자에게 먼저 물어보고 "커밋해줘 / 푸시해줘" 같은 명시적 지시를 받은 뒤에만** 수행한다.
- "명시적 승인"의 기준:
  - 사용자가 그 턴에서 직접 커밋/푸시를 요청했거나("커밋해", "push 해줘"),
  - 사용자가 제안된 커밋/푸시 계획에 대해 명확히 동의했을 때("응 그렇게 해", "진행해").
  - 이전 턴의 승인을 **다음 작업에 재사용하지 않는다.** 승인은 그 작업 1회에 한한다.
- 애매하면 실행하지 말고 **먼저 묻는다.** 침묵·무응답을 승인으로 간주하지 않는다.

## 2. 커밋 전 확인 절차

커밋/푸시가 필요한 상황이면 다음 순서로 진행한다.

1. 변경 사항을 요약해 보여준다 (무엇을, 왜 바꿨는지 + 대상 파일).
2. 제안 커밋 메시지를 제시한다.
3. **"커밋/푸시할까요?"** 라고 묻고 **대기**한다.
4. 사용자의 명시적 승인을 받은 후에만 실행한다.

## 3. 푸시는 더 높은 주의 (되돌리기 어려움)

- `git push` 는 원격을 바꾸는 작업이므로 커밋보다 더 신중히 다룬다. 반드시 별도 승인을 받는다.
- **force push(`--force`, `--force-with-lease`), 이력 재작성(rebase/filter-branch/amend 후 push),
  브랜치 삭제** 등 파괴적 원격 작업은 위험(해시 변경, 협업자 충돌, 되돌리기 곤란)을 **명시적으로 설명**하고
  별도의 승인을 받은 뒤에만 수행한다. 가능하면 백업 브랜치를 먼저 만든다.
- `main`/기본 브랜치로의 직접 push도 승인 대상이다.

## 4. 커밋 신원 (identity)

- 이 저장소의 커밋 author/committer는 **`secututor <secututor@users.noreply.github.com>`** 로 고정한다.
- 실제 이름·회사 이메일 등 개인 식별 정보가 커밋 메타데이터·메시지·문서 내용에 들어가지 않게 한다.
- 이 신원은 `.githooks/pre-commit`, `.githooks/pre-push` 훅으로 강제된다.
  새 클론에서는 훅 활성화를 위해 최초 1회 다음을 실행한다:
  ```
  git config core.hooksPath .githooks
  ```
- 훅을 우회하는 `--no-verify` 사용을 금지한다.

## 5. 스테이징 범위

- `git add .` 로 전체를 무분별하게 담지 말고, **변경 의도에 맞는 파일만** 스테이징한다.
- 비밀정보로 의심되는 파일(.env, 키, 자격증명 등)은 스테이징 전 사용자에게 확인한다.
